# Product assumptions

The brief leaves some behaviour open. Each choice below is deliberate, applied consistently, and covered by tests where it affects behaviour.

| # | Topic | Decision | Reasoning |
|---|---|---|---|
| 1 | Creating accounts | `POST /accounts` requires an `X-Admin-Token` (env `ADMIN_TOKEN`). Everything else uses the account's `X-API-Key`. | The brief says accounts get a key when created but not who may create one. Open creation lets anyone mint accounts. |
| 2 | User identifiers | Callers address users by their own id (`userId`, 1-200 chars of `A-Za-z0-9._:@-`). It is unique per account; two accounts may reuse the same id. | The caller already has this id, so it needs no mapping table. The restricted charset keeps it safe in URLs. The internal uuid never leaves the service. |
| 3 | Unlimited | A plan limit of `null` means no limit for that rule. Limits are integers from 1 up to 1e12 (monthly and daily) and 1e9 (per request). | Lets a plan use only one rule. The caps keep every BIGINT inside a JS number, so no precision loss. |
| 4 | Default plans | A new account gets `starter`; a new user gets `basic`, unless specified. | Every account and user must always have a plan, or the two-plan rule has nothing to apply. |
| 5 | Plan kinds | An *account* plan can only go on an account and a *user* plan only on a user. The database enforces this with composite foreign keys. | Prevents a mix-up that would silently apply the wrong limits. |
| 6 | Plan visibility | An account sees predefined plans plus its own. Another account's plan answers 404, never 403. | Does not reveal that a resource exists in a different account. |
| 7 | Predefined plans | Read-only: `PATCH` returns 403 `predefined_plan_read_only`. | Allowed by the brief. Keeps the documented example limits trustworthy. |
| 8 | Plan names | Unique per owner, case-insensitive. An account may reuse a predefined name for its own plan. | Avoids confusing duplicates inside one account. |
| 9 | Plan deletion | Not supported. | Deleting an assigned plan would orphan users; out of scope. Edit it or reassign users instead. |
| 10 | Not-found vs. invalid | Unknown id gives 404. Wrong kind of plan gives 422 `wrong_plan_kind`. Bad input gives 422 `validation_error`. | Distinct, predictable error codes. |
| 11 | Key rotation | `POST /account/api-key/rotate` returns a new key and invalidates the old one immediately. | A lost or leaked key needs a recovery path. Small addition, high value. |
| 12 | Key storage | Only the SHA-256 hash is stored. The key is shown once. | A database leak does not leak working keys. |

| 13 | Rejection is not an error | `POST /consume` returns HTTP 200 with `accepted:false`, `rule`, `level`, a `message` and the full `violations` list. 4xx is only for bad input, bad key, unknown user, or a reused requestId. | "Not allowed" is the service doing its job. Callers branch on `accepted`, and monitoring does not confuse quota rejections with failures. |
| 14 | Which rule is reported | Fixed order: user per-request, account per-request, user daily, account daily, user monthly, account monthly. The first broken one is `rule`/`level`; every broken one is in `violations`. | Predictable; request-local checks first, then shortest window first, user before account. |
| 15 | Rejected requests | Logged in history, count toward no usage, and own their `requestId`. | Callers can audit denials; counters stay exact. |
| 16 | Retries | `requestId` is unique per account. A retry returns the stored decision with `replayed:true`, even if plans changed since. Same id with a different user or amount gives 409 `idempotency_conflict`. To get a new decision, send a new `requestId`. | Safe retries: a timeout can never double-charge or flip an answer. |
| 17 | Replayed balances | A replay shows the balances as of the original decision, not current ones. | The response is identical; current balances come from the usage endpoints. |
| 18 | Month boundary | The UTC month is taken when the request is **processed**, meaning when it holds the account lock and is being decided, not when it arrived. A request that arrives at 23:59:59.9, queues, and is decided at 00:00:00.1 counts in the new month (the code re-reads the clock after taking the lock and, if the month turned, locks and charges the new month). | Matches "new usage belongs to the UTC month when it is processed"; tested with a clock that turns during the queue. |
| 19 | Reduced allowance | `remaining = max(0, allowance - used)`; consumption is rejected at that level until allowance exceeds usage again. Usage is never rewritten. | Brief. |
| 20 | Unknown user on consume | 404; nothing is auto-created and nothing is logged. | Users are registered explicitly, so typos fail loudly. |
| 21 | Plan edits mid-request | A request uses the plans read once after it takes its locks. | Never a mix of old and new limits; see CONCURRENCY.md. |
| 22 | `remaining` for past months | Only the current month reports `remaining`; for past months it is `null` and `used` is the record. | "Remaining" means what can still be consumed, which is meaningless for a closed month, and recomputing it against today's plan would be misleading. |
| 23 | Future periods | `period` after the current UTC month gives 422 `future_period`. A past month with no activity returns zeros. | Nothing can exist in the future; zeros for quiet months are truthful. |
| 24 | Usage lists every user | `/usage` includes users with 0 usage. | A complete roster is easier to reconcile than a sparse one. |
| 25 | History scope | `/requests` returns decisions (accepted and rejected), newest first, with the limits that applied then, filterable by user, month and outcome. It never rewrites when plans change. | Brief: changes must preserve past request history. |
| 26 | Reads are not locked | Usage/limits/history read committed data without locks, so a value may be a few milliseconds behind a request in flight. | Reads must not slow the write path; decisions never depend on these reads. |
| 27 | Read consistency | `/usage` and `/users/{id}/usage` run in one `REPEATABLE READ` read-only snapshot, so the account total and the per-user rows in a single response always agree (account = sum of users). Different requests may of course see different instants. | A response that contradicts itself would look like a bug to the caller. A test failed 3 of 3 times when the snapshot was removed. |
| 28 | History order | `created_at` is stamped after the lock is granted (`clock_timestamp()`), so ordering by it is the order decisions were made, and the `applied` balances in history run forward in time. | `now()` is the transaction's start time, before the lock wait, which would let a later decision look older and be skipped by a cursor. |
| 29 | Client strings | Plan ids, plan names, account names and request ids may not contain control characters (including NUL). Plan ids are `[A-Za-z0-9_.:-]` up to 100 chars; names up to 100/200; `requestId` up to 200. Any other invalid value the database rejects is mapped to 422 `invalid_input`. | NUL and similar make PostgreSQL throw; a client mistake must be a 4xx, not a 500. |
| 30 | Periods | A `period` must be `YYYY-MM` between 1970-01 and 9999-12 and not in the future. | PostgreSQL cannot store year 0 as a date; earlier years are meaningless here. |
| 31 | Abuse limits | An account may have at most 100 custom plans and 100,000 users (403 `account_limit_reached`). Admin endpoints are rate-limited per IP (`ADMIN_RATE_LIMIT_PER_MIN`, default 600, 429 `rate_limited`). At most `ACCOUNT_QUEUE_MAX` (default 1000) consumes wait behind one account in one process; beyond that the service answers 503 `account_busy` (retry shortly). | One key holder or one hot account must not be able to grow the database or the memory of the service without bound. The numbers are generous defaults, not product rules. |
| 32 | Lost keys | `POST /accounts/{id}/api-key/rotate` (admin token) issues a new key for an account that lost its own; the old key stops working at once. | The account's own rotate endpoint needs the old key, so an admin path is needed. |
| 33 | Demo defaults | Compose ships a demo `ADMIN_TOKEN` so `docker compose up --build` works with no setup. The service logs a warning at start when it sees that value. Compose publishes the service and client ports on all interfaces by default so the start works on every Docker setup; set `BIND_ADDR=127.0.0.1` in `.env` to keep them local, and set `ADMIN_TOKEN` before exposing the service. | The brief requires a one-command start; the risk is stated, not hidden. |
| 34 | The extra rule | A **daily allowance** (units per UTC calendar day) was added to both plan kinds, evaluated like the monthly one. Full reasoning and interaction with account and user plans: [ADR-007](decisions/ADR-007-daily-allowance.md). | The brief makes extra rules optional but asks that any be explained and demonstrated. This one fits the existing design (same lock, same counter pattern) without weakening the core. |
| 35 | Daily vs monthly | A daily allowance is not validated against the monthly one. Larger than the monthly: harmless (the monthly rule still binds). Smaller: it binds first on the day. | Plans are edited independently and at any time; a cross-field rule would make valid edits fail depending on order. |
| 36 | When a day starts | The UTC day (00:00-24:00) in which the request is **processed** (same instant as the month; a request queued across midnight is charged to the new day). There is no per-account time zone. | One clock, one definition, easy to test; matches the UTC month in the brief. |
| 37 | Daily numbers in responses | `dailyAllowance`, `usedToday`, `remainingToday` describe today; they are `null` when there is no daily limit and for past months. Decisions stored before the rule existed read back with `null` daily fields. | "Today" means nothing for a closed month; old history must stay readable. |
| 38 | Predefined plans | The four predefined plans got example daily limits: Starter 2,000, Pro 100,000, Basic 100, Premium 1,000. | Demonstrates the rule with the ready-to-use plans; custom plans choose their own. |
